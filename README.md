# dqkit: Rules-Driven Data Quality Toolkit (synthetic research data)

A small Python tool that cleans research-style tables, checks them against rules written in a YAML file, runs cross-database comparisons in SQL, and produces a discrepancy report that says what is wrong, how serious it is, and who should fix it.

All data is synthetic and generated by the code. No real participants. This is a practice project built to learn research data management workflows, not an official tool of any organization.

## What it does

1. **Generates** a synthetic dataset (200 participants, ~780 visits, ~580 cognitive screens, plus a separate "clinical database" table) with **69 errors planted on purpose** and an answer key listing every one.
2. **Cleans** safe problems automatically and logs each change: label variants, date formats, exact duplicates.
3. **Validates** every field against `rules/rules.yaml`: required, type, pattern, allowed values, min/max.
4. **Checks relationships**: duplicate keys, orphan IDs between tables, score totals that do not match item scores.
5. **Runs SQL** (`sql/cross_checks.sql`) on an in-memory database for visit dates before enrollment and for differences between the research and clinical databases.
6. **Reports** to CSV, Excel (Summary, Needs Review, Auto-fixes sheets) and Markdown, grouped by the team that should resolve each issue.
7. **Exports** a REDCap-style data dictionary from the same rules file.
8. **Verifies itself**: compares what it found with the answer key. All 69 planted errors are found, with no misses and no extras. A clean dataset produces zero issues. The same check runs in GitHub Actions.

## Quick start

```bash
pip install -r requirements.txt
export PYTHONPATH=src

python -m dqkit generate
python -m dqkit check --answer-key data/answer_key/planted_errors.csv
python -m dqkit dictionary
python -m pytest
```

Without pytest installed, the tests also run with `python -m unittest discover -s tests`.

Outputs appear in `output/`: `discrepancy_report.xlsx`, `discrepancy_report.md`, `issues_log.csv`, `cleaned/`, `data_dictionary.csv`.

## Reusing it on other data

Edit `rules/rules.yaml` to describe different tables and fields, and add queries to `sql/cross_checks.sql` (each query returns `record_key`, `field`, `value`, `message` and carries a `-- category:` and `-- table:` comment). No Python changes are needed for new fields or ranges. A test changes a rule and confirms the results change.

## Layout

```
rules/rules.yaml        field rules, categories, severity, routing
sql/cross_checks.sql    cross-table and cross-database checks
src/dqkit/              generate, cleaning, validate, sqlchecks, report, cli
tests/                  16 tests, including the exact-match answer-key test
docs/                   SOP and data dictionary notes
.github/workflows/      CI: tests, answer-key match, clean-data check
```

## Limits (said plainly)

- The data and the errors are synthetic. Real data has messier problems than the ones planted here.
- The data dictionary follows the REDCap column layout but has not been imported into a REDCap project.
- The tool is a command line script, not a database or a web application.
- Dates are compared as ISO text after cleaning. This is correct for YYYY-MM-DD and would need changing for other formats.
- Cross-database sex comparison only covers the coded values F and M. Other values are caught by field validation.
- Rules are not yet able to express conditional logic, for example "required only if another field is yes".
